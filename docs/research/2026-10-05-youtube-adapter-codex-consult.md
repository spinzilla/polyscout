## 总判断

**【推断】YouTube 在技术上适合新增，但不宜作为"B站翻版"直接克隆。首版采用官方搜索与元数据 API、用户自带代理；字幕能力单独设准入条件；不加入 Piped 自动回退和音频下载 ASR。版本上建议暂时维持原路线图。**

## 1. 三个被纠正的前提

- **【确定】B站 ASR 尚不是已冻结的可复用能力。** Q7 第三轮修订：v0.2 仅做 CC/AI 字幕，音频下载与 ASR 延后单独评审。「已有成熟 ASR 管道顺手复用」不成立。
- **【确定】全球用户定位不等于必须覆盖全球平台。** Q1 完整定位是面向全球 agent 生态的「中文平台穿透引擎」；YouTube 有扩展价值，但不是英文 README 成立的必要条件。
- **【需验证】「住宅 IP 是最优方案」证据不足。** 底稿引文谈的是轮换住宅代理；推不出用户当前 Clash 出口稳定可用，也推不出「零成本」「机房 IP 必被封」。代理客户端、出口类型、平台接受程度是三个不同问题。

## 2. 代理能力：Settings 配置，客户端构造执行，adapter 声明边界

**【确定】当前 Transport 接收已构造的 httpx.AsyncClient，无代理配置；Settings 也无对应字段。**

**【推断】职责划分建议：**

| 层级 | 建议职责 |
|---|---|
| Settings | 读取、校验代理配置，解析覆盖关系，保管敏感字段 |
| 客户端构造层 | 按已解析的路由创建客户端，负责关闭资源 |
| Transport | 统一请求预算、计数、超时、响应上限、错误脱敏和禁止重试 |
| adapter 声明 | 说明访问通道和代理使用边界，不携带代理地址或凭据 |

**【推断】配置建议：**

```text
POLYSCOUT_PROXY                  # 信源请求的默认代理
POLYSCOUT_YOUTUBE_PROXY          # YouTube 覆盖：代理 URL 或 direct
POLYSCOUT_YOUTUBE_API_KEY        # 用户自带官方 API key
```

- 覆盖顺序「信源显式设置 → 全局设置 → 直连」；未设置=继承，`direct`=明确直连，避免空串语义不清。
- 全局变量只作用于信源；本地 LLM 不应被意外送往代理。
- YouTube 应描述为「支持代理、部分部署环境依赖代理」，不硬编码「必须代理」。代理故障应产生缺口，不应静默改直连。
- 现有 `endpoint()` 不适合直接复用为代理校验器（拒绝 URL 凭据、仅允许 HTTPS 或回环 HTTP）。
- MVP 可先限定本地 HTTP 代理；SOCKS、远程认证代理另行确认依赖与安全边界。代理密码/完整地址不得进日志和 manifest。
- 环境代理变量是否参与路由应显式确定，避免配置外隐藏出口。

**【推断】Q5 建议增补代理条款（不能写成反风控豁免）：**

> 允许用户配置自有代理作为预先确定的网络传输路径；项目不提供、收集或分发代理凭据。出现验证码、访问拒绝或限流信号后，不通过更换代理、出口或中转服务继续访问同一信源。

**【确定】与现有硬墙契约一致**（契约已禁止碰壁后换凭据、代理或同一目标的其他通道）。

## 3. 搜索：官方 Data API 主通道，不做自动双通道降级

| 方案 | 结论 |
|---|---|
| 官方 Data API | **【推断】首版采用**，负责搜索和视频元数据；缺 key 返回 `youtube_key_not_configured`，其他 adapter 继续 |
| Piped 公共实例 | **【推断】不纳入默认路径**（第三方信任、隐私与维护成本） |
| 官方失败后自动切 Piped | **【确定】若失败属硬墙，与当前契约冲突** |

- 未来若支持 Piped：用户预先选定的 provider、固定实例、独立声明；不动态遍历公共实例找可用出口，不作官方配额耗尽后的绕行。
- **【需验证】不足以确认当前配额数字与免费政策**（底稿「独立搜索桶」与「每次 100 units」并存且多为转引）。「重试只烧第二天额度」无足够证据，应改为「配额拒绝后停止，不自动重试」。
- 预算实现：同时记录请求次数与配额估算，区分搜索/分页/详情。按现有架构上限（每轮 3 查询 × 2 轮）设计上限约 6 次搜索 + 6 次详情——这是建议预算，不是已验证官方额度。
- **【确定】当前 Transport 在读正文前把所有 403 判为硬墙**，无法区分 quotaExceeded/权限/key 问题；细分需设计受限、脱敏的错误解析，不能让 adapter 绕过统一传输层。

## 4. 字幕：先解决准入，再讨论回退与可信度

**【推断】发布优先级：**

1. 官方元数据作为基础能力。
2. 访问政策核验通过后，增加匿名 timedtext 字幕。
3. Piped 字幕仅作为将来可选的预配置来源。
4. 首版不做下载音频 ASR。

- **【需验证】timedtext 是否满足 Q5 材料不足**：未文档化、无需登录、浏览器会调用，都不等于平台允许第三方自动采集。可作技术候选，不能宣布为合规默认链路。
- **【确定】「没有字幕」与「遇到硬墙」必须分开**：前者记 `subtitle_unavailable` 并保留元数据；后者熔断整个 YouTube adapter，本次运行不再访问其他视频或切 Piped（熔断粒度 = adapter）。
- credibility 按来源定级：

| 材料 | 建议等级 | 解释边界 |
|---|---|---|
| 官方 API 返回的视频字段 | `primary` | 对平台字段是一手记录，不证明视频主张正确 |
| 直接获取的平台字幕（含自动字幕） | `primary` | 对「平台提供的这条字幕文本」是一手记录，不保证忠实还原语音 |
| Piped 转交、未独立核对的字幕 | `secondary` | 中转方；无法确认对应关系时降为 `unknown` |
| 本地 ASR 输出 | `secondary` | 机器生成的派生材料，不能冒充作者原文 |
| 来源或视频身份无法确认 | `unknown` | 即便可读，也不能提升等级 |

- 字幕证据还应记录：视频 ID、语言、人工/自动/翻译类型、获取通道、片段时间范围——**当前 Observation 缺这些字段且禁止未知字段，需显式演进 schema**。
- 字幕摘录保持原语言原片段；翻译和总结另行展示。不能用多渠道返回同一字幕制造「独立多源佐证」。

## 5. ASR：从 YouTube 首版删除自动下载兜底

- **【推断】删除的是「没有字幕就自动 yt-dlp 下载音频」这条路径**，不是否定 ASR 技术。后续可单独评审「用户提供本地音频」或「已有明确授权来源」的转录功能。
- **【确定】两个约束须分别判断**：「不建镜像库」约束持久保存和输出方式；「尊重 ToS」约束访问、下载及使用方式。临时下载+删除可能满足前者，**不能自动满足后者**。可选依赖、用户勾选、仅供研究，都不能替代具体访问授权。
- **【需验证】无法依据现有材料认定音频下载或字幕提取的法律责任范围**。底稿「主要是合同风险」「暴露面远小于 youtube-dl」结论过强；youtube-dl 仓库恢复案例不提供本项目通用许可。
- **【推断】若未来评审通过**，ASR 还需独立的大小/时长/计算/临时文件预算与取消、异常、崩溃清理设计；文本请求的 2 MB 上限与 20s 超时不应整体放宽。

## 6. Compliance 块：声明实际边界，不声明已经合法

**【推断】首版（官方搜索和元数据）文案候选：**

```python
Compliance(
    terms_url="https://www.youtube.com/t/terms",
    access_policy=(
        "仅通过 YouTube Data API 获取公开视频搜索结果与元数据，"
        "使用用户自带 API key；不使用 YouTube 登录态，不下载媒体。"
        "代理仅作为运行前配置的网络路径；访问拒绝或限流后停止，"
        "不更换出口或中转服务继续访问。"
        "使用还须满足适用的 API 服务条款与开发者政策。"
    ),
    robots_policy=(
        "本配置不抓取视频 HTML 页面或未文档化字幕端点。"
        "官方 API 的使用受其访问政策约束；"
        "本声明不构成对其他网页路径的 robots 许可。"
    ),
    retention="excerpts_and_links_only",
    cookies_supported=False,
    wall_action="open_circuit_for_run",
)
```

- **【推断】若以后启用 timedtext，声明必须随配置变化**：明确写出「匿名访问未文档化字幕接口」，包括依赖可能产生的视频页或其他请求。
- **【推断】API 数据的缓存、刷新、删除、署名及展示要求也应进入后续核验**；「只保存摘录」不必然满足这些要求，永久 JSONL 证据是否需要保留策略目前不能确认。

## 7. 版本：建议维持 v0.3 = CSDN + MCP

- **【确定】提前 YouTube 至少涉及 Q4 信源范围和 Q11 发布节奏的显式修订**；原路线图还包含 MCP，不能只说「CSDN 顺延」却遗漏 MCP 去向。
- **【推断】不建议仅凭「代码热乎」调换版本**：代理隔离、第三方库传输接入、字幕准入、证据 schema、维护预算比克隆 adapter 的代码成本更影响交付。
- **【推断】YouTube 列为后续候选，满足以下条件后再决定插队：**
  - 官方搜索与元数据在授权环境中实测通过。
  - 字幕访问边界有明确结论；若没有，用户明确接受元数据版价值。
  - 第三方依赖所有网络请求都受预算、熔断和取消控制。
  - 明确 CSDN、MCP 的新位置及 Q4/Q11 修订。
  - 证明相比现有 websearch，它带来可观察的额外证据价值。
- **【需验证】材料没有 CSDN 的工作量、阻断情况和用户需求比较**，不足以判断两者完整投入收益排序。

## 8. 额外盲点与实现阻断

| 风险 | 判断及建议 |
|---|---|
| 第三方库绕过 Transport | **【需验证】** 未读其源码，不能确认请求、重试、cookie 和代理行为。单纯调库不继承项目契约；必须覆盖全部内部请求。 |
| 同步调用与取消 | **【需验证】** 需确认库的调用模型；线程包装阻塞调用时，外层取消不代表内部网络立即停止。 |
| 元数据成功、字幕失败 | **【确定】** 基类捕获 FetchError 后只返回失败记录；adapter 直接抛错会丢未返回的元数据。参考 GitHub 实现：保留已完成记录并追加缺口。 |
| 平台错误藏在成功响应内 | **【推断】** 需识别播放器、字幕接口的专有错误，不能只靠 HTTP 状态和通用关键词。 |
| Piped 返回任意 URL | **【推断】** 需防止请求被引向内网或非预期主机（SSRF）；实例返回的字幕地址不能直接当可信目标。 |
| 代理与 cookie 隔离 | **【确定】** Transport 允许调用方显式传 cookie，声明字段本身不执行权限隔离。YouTube 零 cookie 约束需要实际保证，不能照搬 B站凭据路径。 |
| 规划器尚不接受 YouTube | **【确定】** `Query.adapter` 只允许 github/websearch/bilibili；新增类不足以接入。总查询上限仍为六条，多源覆盖策略也要明确。 |
| 健康探针成本 | **【推断】** 应区分官方 API、字幕通道和代理出口健康；单出口失败 ≠ adapter 全面失效，公共 CI 不应自动轮换代理。 |
| 社区观感 | **【推断】** 文档应介绍网络配置和失败边界，避免宣传「住宅代理解封」「永久穿透」，否则与宪法和 best-effort 承诺冲突。 |
